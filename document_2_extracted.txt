Phase 2 – Testing Plan and Defect Discovery

Given the site’s inaccessibility to automated tools, we propose a comprehensive test suite (to be executed once manual access is arranged). Below are key test cases; actual execution status is NOT RUN/BLOCKED until we have a live session.

Frontend / UX Testing (Manual):

We will test every route and control in a full browser session. Each action (clicking buttons, submitting forms) should produce expected UI changes or errors. We will check:

Routing & Navigation: Test that links or menu items (Home, Login, Dashboard, About, Help, etc.) navigate correctly without errors or broken links.

Controls & Forms: Verify all form fields accept valid input, enforce limits (e.g. numeric ranges, required fields), and give clear error messages for invalid input. For example, if there is a “Project name” field, it should reject empty strings or extremely long names.

Duplicate Submissions: Ensure forms disable the submit button while processing to prevent double submits.

State Management: Check that UI state updates (e.g. enabling/disabling buttons, showing spinners) correctly reflect background operations.

Responsive Layout: Resize the browser and test on mobile resolutions; ensure no content overlaps or disappears. Check key pages (landing, dashboard, report) for proper mobile layout.

Accessibility: Use keyboard-only navigation to tab through all interactive elements; ensure focus indicators are visible. Test with a screen reader for meaningful labels. Check color contrast ratios against WCAG 2.1 standards.

Data Display: Inspect any tables or plots (if present) for proper axis labels, units, legends, and scientific notation format. Verify that empty or invalid data is handled gracefully (e.g. “No data available”).

File Uploads: If geometry or data file upload is offered (e.g. CSV, DAT, STEP), test with correct and incorrect file types and sizes. The UI should validate file type, size, and show progress/error messages as needed.

Data Export: If there is a “Download results” or “Export” feature, test it produces a correctly formatted file (CSV, PDF, etc.) with complete data. Handling of name collisions or large files should be tested.

For each of the above, we will document steps, expected behavior, actual results, and screenshots or logs where discrepancies occur. All user-UI interactions should be reproducible.

Phase 3 – Aerospace Scientific Validity and Engineering Trust

Scope: We must treat any claimed CFD/simulation/AI computation very conservatively. No “push-button” results can be trusted for critical decisions without rigorous validation. We will apply standard Verification & Validation (V&V) best practices:

Dimensional Consistency: Ensure all inputs/outputs have consistent units (m vs ft, kg vs lb, etc.) and coordinate conventions. The UI must label axes and reference areas clearly. (No external reference needed; this is best practice.)

Conservation Laws: Any CFD solver should conserve mass, momentum, and energy to numerical precision. We will check this in results for closed systems (e.g. fluid in-out balance).

Mesh Convergence: For any CFD solver, results should be insensitive to mesh refinement. For each case, perform at least 3 grid sizes and verify solution convergence (e.g. drag changes <1% between finest meshes).

Solver Convergence: Monitor residuals; ensure solvers actually converge (residual drop) rather than stop early. Check that outputs (force coefficients, pressure) stabilize before reporting.

Modeling Assumptions: Document turbulence models (e.g. k-ε, RANS vs LES), boundary conditions (inlet profiles, far-field treatments), and material properties. These must match the chosen benchmark. Any default should be overridden if needed.

Reproducibility: Every calculation must log its full config (geometry file version, solver version, seed values, mesh, date, etc.). We will insist on exporting this provenance so simulations can be repeated. (NIST’s focus on trustworthy AI underlines the need for traceable scientific results.)

Benchmarking: We will assemble a suite of reference cases from literature for validation (pressure drag of NACA0012 airfoil, ONERA M6 wing at transonic Mach, NASA Common Research Model wing, turbulent channel flow, etc.). For each, we know expected physical behavior:

Example 1: 2D flat-plate Couette flow (analytic solution) – predicts linear velocity profile. The code’s solution should match exact formula to <0.5% error (a very strict numeric check).

Example 2: NACA 0012 airfoil at Re=6e6, Mach=0.2 – expected CL vs α should agree within a few percent with published data (e.g. Abbott & von Doenhoff).

Example 3: ONERA M6 wing transonic flow – compare Cp distribution and lift/drag with NASA results (within ~5%).

Example 4: Cylindrical incompressible flow (Kármán vortex street) – check Strouhal number matches theory for given Re.

Example 5: Simple rocket exhaust (expanding gas) – verify mass flow and thrust against isentropic flow equations if possible.

Uncertainty Quantification: Provide error bars or confidence ranges. For surrogate/AI models, use cross-validation on held-out test cases. For simulation runs, estimate numerical uncertainty (e.g. Grid-Convergence Index).

Out-of-Domain Detection: If a user requests a simulation outside the training range of a surrogate, the system must warn or refuse. For example, a surrogate trained on subsonic flows should not blindly extrapolate to supersonic speeds.

Value Separation: Clearly label whether values are measured (e.g. from experiments), simulated, or estimated by AI. E.g. “CD (simulated)” vs “CL (NASA data)”. Mixing them without labeling can mislead.

Version Control: Keep version tags for all solvers, libraries, and models. Results should cite the software version used. (This aligns with NIST’s emphasis on reproducibility.)

Physical Limits: Sanity-check outputs. Lift coefficients should not exceed theoretical limits by orders of magnitude; no negative densities or absurd Mach >10 unless enabled. Outliers must trigger flags.
